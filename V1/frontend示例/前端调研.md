## 一、功能需求

### 1.1 核心功能

- **对话式任务发起**：以聊天交互的方式输入研究数据提取需求，支持自然语言描述任务目标、上传 PDF 文献等附件
- **查看 State**：实时查看工作流各节点的状态数据，包括每个子图的输入/输出 State 快照
- **查看 Workflow**：以可视化流程图展示完整的四子图工作流（意图澄清 → 检索 → 提取 → 数据质量），支持节点展开/折叠
- **查看 Agent 执行**：追踪每个子图内部 Agent 的执行过程，包括 Agent 间的消息传递、路由决策
- **查看 Tool 调用**：展示每个 Agent 调用的工具（如 VLM、OCR、数据库检索等），包括工具输入参数和返回结果
- **查看 LLM 推理**：展示 LLM 的推理链（Chain-of-Thought），包括 prompt 构造、模型输出、结构化解析结果
- **查看每个 Stage 的输入输出**：以可对比的方式查看四个子图各阶段的输入数据和输出结果
- **查看 Quality Report**：展示数据质量评估报告，包括完整性、一致性、规范性等维度的评分和具体问题
- **Debug 整个 Workflow**：支持断点查看、步骤回放、状态回溯等调试能力，方便定位工作流中的问题

### 1.2 辅助功能

- **任务历史管理**：保存历史任务记录，支持查看、重试、对比不同任务的结果
- **实时日志流**：提供可过滤的实时日志面板，展示工作流运行过程中的详细日志
- **数据导出**：支持将提取结果以 JSON / CSV / Excel 等格式导出
- **错误提示与恢复**：当工作流某阶段出错时，给出清晰的错误定位和重试建议

## 二、设计哲学与风格参考

### 2.1 整体风格定位

我们的前端风格对标当前主流 AI 智能体产品，追求**简洁、专业、可信赖**的视觉体验。作为一个科研数据提取工具，界面需要在"降低认知负担"和"展示复杂信息"之间取得平衡——既要让非技术用户也能轻松上手，又要为开发者提供足够的调试深度。

### 2.2 参考产品分析

#### ChatGPT 风格要素

ChatGPT 的界面设计已成为 AI 产品的交互范式标杆，我们希望借鉴以下核心要素：

- **左侧边栏 + 主内容区**的经典布局：左侧展示对话/任务历史列表，右侧为当前任务的主工作区。这种布局已被用户广泛熟悉，学习成本极低
- **对话式交互**：用户通过自然语言输入任务需求，系统以流式输出（streaming）的方式逐步展示处理过程和结果，让用户感受到"AI 正在工作"
- **流式文本渲染**：LLM 的输出以打字机效果逐字展示，配合 Markdown 渲染（代码高亮、表格、公式等），既美观又实用
- **消息气泡的最小化**：不使用传统的气泡框，而是让 AI 的回复以"文档流"的形式自然铺展在内容区，减少视觉噪音
- **底部固定输入栏**：输入框固定在页面底部，支持文件上传附件、快捷指令等，符合用户已有的交互习惯

#### Codex / Claude Artifacts 风格要素

Codex 和 Claude 的 Artifacts 功能展示了如何在 AI 对话的基础上叠加**结构化的工作流可视化**，这正是我们需要的：

- **分栏式工作区**：左侧为对话/日志流，右侧为结构化的内容展示区（代码预览、文档预览、流程图等）。在我们的场景中，右侧可以展示工作流可视化、数据预览、质量报告等
- **执行过程的透明化**：每一步操作都有清晰的状态指示（等待中 → 执行中 → 完成/失败），用户可以实时看到"AI 正在做什么"
- **可折叠的过程详情**：默认展示精简的执行摘要，用户点击可展开查看详细的工具调用、LLM 推理过程等，避免信息过载
- **代码/数据的高亮展示**：对于结构化数据（JSON、表格等），使用语法高亮和格式化展示，提升可读性

#### LangGraph Studio 风格要素

作为同样基于 LangGraph 构建的智能体，LangGraph Studio 的可视化设计对我们有直接参考价值：

- **图结构可视化**：将 Agent 工作流以有向图的形式展示，节点表示 Agent/工具，边表示消息传递路径，直观呈现工作流拓扑
- **节点状态着色**：通过颜色编码表示节点当前状态（灰色=等待、蓝色=执行中、绿色=完成、红色=错误），一眼掌握全局进度
- **节点详情面板**：点击图中的任意节点，右侧弹出该节点的详细执行信息（输入、输出、中间状态、耗时等）

### 2.3 我们的设计原则

基于以上参考产品，提炼出以下设计原则：

1. **渐进式信息披露（Progressive Disclosure）**：默认展示高层摘要，按需逐层展开细节。用户首先看到"任务进行中（2/4 阶段完成）"，点击可看到子图级别，再点击可看到 Agent 级别，再点击可看到工具调用级别
2. **实时反馈（Real-time Feedback）**：工作流执行的每个阶段都应有实时状态更新，避免用户面对一个"黑箱"等待。通过 WebSocket 推送事件流，前端实时渲染执行进度
3. **对话 + 结构化的双模态展示**：继承 ChatGPT 的对话式交互作为主入口，同时在侧边栏或内嵌面板中展示结构化的工作流视图、数据表格、质量报告等
4. **科研专业感**：视觉上保持克制和专业，避免过于花哨的动效。配色以冷色调为主（深蓝/灰/白），强调数据的清晰可读性。字体选择等宽字体用于代码/数据展示，无衬线字体用于 UI 文本

## 三、前端技术栈

### 3.1 React 18+

**选择理由**：React 是目前生态最成熟、社区最活跃的前端框架，拥有丰富的组件库和工具链。对于我们的项目而言，React 的组件化开发模式非常适合构建复杂的可交互界面（工作流图、数据表格、调试面板等），且 React Flow 等可视化库与 React 深度集成。

**关键特性利用**：

- **Concurrent Mode / Suspense**：用于处理流式数据的并发渲染，在 LLM 输出流式到达时不阻塞 UI 交互
- **useTransition / useDeferredValue**：在渲染大量日志或工作流节点时保持 UI 响应性
- **Server Components 预留**：虽然目前前后端分离，但 React Server Components 的模式可以在未来优化首屏加载

### 3.2 TypeScript

**选择理由**：TypeScript 的类型系统对于我们的项目至关重要——工作流的 State 结构复杂（包含多个子图的嵌套状态），Agent 的输入输出有严格的 Schema 定义，使用 TypeScript 可以在前端层面就捕获数据结构不匹配的问题，减少联调成本。

**关键应用场景**：

- **工作流 State 类型定义**：与后端 Pydantic Model 对应，定义前端的 TypeScript Interface，确保数据结构一致
- **API 响应类型安全**：配合 TanStack Query 的泛型，实现从 API 请求到 UI 渲染的全链路类型安全
- **React Flow 节点类型扩展**：为工作流可视化定义自定义节点类型，每种节点携带不同的数据结构

### 3.3 Vite

**选择理由**：Vite 基于原生 ES Module 的开发服务器启动速度远快于 Webpack，在开发体验上显著提升效率。同时 Vite 对 TypeScript、React JSX、CSS Modules 等有开箱即用的支持，配置成本极低。

**关键配置**：

- **路径别名**：配置 `@/` 指向 `src/`，简化组件导入路径
- **环境变量管理**：通过 `.env` 文件管理 API 地址、WebSocket 地址等环境相关配置
- **构建优化**：利用 Vite 的 Rollup 打包进行代码分割（Code Splitting），将 React Flow、ECharts 等大型库按需加载

## 四、UI 框架与组件

### 4.1 Tailwind CSS

**选择理由**：Tailwind 的原子化 CSS 方案非常适合快速迭代 UI 原型，同时保持样式的一致性。通过 Tailwind 的设计令牌（Design Tokens）系统，可以统一管理颜色、间距、圆角、字体等视觉变量，确保整个项目的视觉风格统一。

**关键使用规范**：

- **设计令牌预定义**：在 `tailwind.config.ts` 中定义项目的主题色板（primary、secondary、accent、muted 等），所有组件通过语义化的 class 名引用，不直接写死颜色值
- **暗色模式预留**：Tailwind 原生支持 `dark:` 前缀，虽然首版可能不做暗色模式，但在设计令牌层面预留切换能力
- **响应式布局**：利用 Tailwind 的断点系统（`sm:`、`md:`、`lg:`、`xl:`）实现不同屏幕尺寸下的自适应布局

### 4.2 shadcn/ui

**选择理由**：shadcn/ui 不是传统的组件库（不通过 npm 安装），而是将高质量的组件代码直接复制到项目中，完全基于 Radix UI 和 Tailwind CSS 构建。这意味着我们可以完全控制组件的实现细节，按需修改，不会被"黑箱组件"限制。对于比赛项目来说，这种灵活性非常重要——我们需要快速定制出独特的界面效果。

**核心使用的组件**：

- **Layout 类**：`Sheet`（侧边抽屉）、`Resizable Panel`（可拖拽分栏）、`Scroll Area`（自定义滚动区域）
- **数据展示类**：`Table`（数据表格）、`Card`（信息卡片）、`Collapsible`（折叠面板）、`Accordion`（手风琴）
- **反馈类**：`Alert`（提示信息）、`Toast`（轻量通知）、`Progress`（进度条）、`Skeleton`（骨架屏加载态）
- **交互类**：`Dialog`（对话框）、`Dropdown Menu`（下拉菜单）、`Command`（命令面板，用于快捷操作）
- **表单类**：`Input`、`Textarea`、`Button`、`Select`、`Checkbox`（用于任务配置和筛选）

### 4.3 图标与动效

- **Lucide React**：shadcn/ui 推荐的图标库，轻量且风格统一，覆盖常用的文件、代码、设置、箭头等图标
- **Framer Motion**（可选）：用于关键交互的微动效，如面板展开/折叠的过渡动画、节点状态切换的渐变效果等。保持克制，不滥用动效

## 五、状态管理与数据层

### 5.1 Zustand（全局 UI 状态）

**选择理由**：Zustand 是极简的 React 状态管理方案，API 比 Redux 简单得多，同时支持 middleware（如 devtools、persist）。我们的全局 UI 状态并不复杂（当前选中的任务、侧边栏展开状态、主题设置等），Zustand 的轻量级方案完全够用。

**管理的状态**：

- `currentTaskId`：当前正在查看的任务 ID
- `sidebarOpen`：左侧边栏的展开/收起状态
- `activeView`：当前激活的视图模式（对话视图 / 工作流视图 / 调试视图）
- `expandedNodes`：工作流图中展开的节点集合
- `theme`：主题设置（预留）

### 5.2 TanStack Query（服务端状态）

**选择理由**：TanStack Query（即 React Query）是管理服务端数据的最佳实践，自动处理缓存、重试、轮询、乐观更新等复杂逻辑。我们的前端大量数据来自后端 API（任务列表、任务详情、质量报告等），TanStack Query 可以让我们专注于 UI 渲染而非数据获取的样板代码。

**关键使用场景**：

- **任务列表查询**：`useQuery(['tasks'], fetchTasks)` 获取历史任务列表，自动缓存和后台刷新
- **任务详情查询**：`useQuery(['task', taskId], fetchTaskDetail)` 获取单个任务的完整数据，包括各阶段结果
- **质量报告查询**：`useQuery(['task', taskId, 'quality'], fetchQualityReport)` 获取数据质量评估报告
- **数据变更**：`useMutation` 处理创建新任务、重试失败步骤等操作，成功后自动失效相关查询缓存

### 5.3 WebSocket 实时数据流

**选择理由**：工作流执行过程中的状态更新、LLM 流式输出、日志推送等场景需要服务端主动推送数据到前端，WebSocket 是最直接的实时双向通信方案。

**设计方案**：

- **连接管理**：创建一个 WebSocket 连接管理器（可封装为 Zustand store 或 React Context），在任务开始时建立连接，任务结束或页面离开时关闭
- **事件类型定义**：使用 TypeScript 定义严格的事件类型体系：

```typescript
// 基础事件类型
type WSEvent =
  | { type: 'stage_start'; stage: StageName; timestamp: number }
  | { type: 'stage_complete'; stage: StageName; output: StageOutput; timestamp: number }
  | { type: 'stage_error'; stage: StageName; error: string; timestamp: number }
  | { type: 'agent_message'; agent: AgentName; content: string; timestamp: number }
  | { type: 'tool_call'; tool: ToolName; input: unknown; output: unknown; timestamp: number }
  | { type: 'llm_stream'; token: string; finish_reason?: string }
  | { type: 'log'; level: LogLevel; message: string; timestamp: number }
```

- **流式渲染**：LLM 的输出通过 `llm_stream` 事件逐 token 推送，前端使用 `requestAnimationFrame` 节流渲染，实现流畅的打字机效果
- **断线重连**：实现指数退避的自动重连机制，重连后通过任务 ID 恢复丢失的事件

## 六、Workflow 可视化

### 6.1 React Flow

**选择理由**：React Flow 是 React 生态中最成熟的流程图/节点编辑器库，支持自定义节点、边、布局算法，且性能优秀（基于 SVG 渲染）。LangGraph Studio 也是类似的节点可视化方案，React Flow 可以帮我们实现接近的效果。

**实现方案**：

- **四层嵌套结构**：
  - **第一层（总览）**：展示四个子图作为四个大节点，用边连接表示数据流向（意图澄清 → 检索 → 提取 → 数据质量）
  - **第二层（子图展开）**：点击某个子图节点后展开，展示该子图内部的 Agent 拓扑（如提取子图中的 VLM Agent、OCR Agent、验证 Agent 等）
  - **第三层（Agent 详情）**：点击某个 Agent 节点后，右侧面板展示该 Agent 的执行详情（输入、输出、工具调用列表、LLM 推理链）
  - **第四层（工具调用详情）**：点击某条工具调用记录，展示工具的完整输入参数和返回结果

- **自定义节点设计**：
  - 每个节点显示：Agent/工具名称、状态图标（spinner/check/error）、耗时
  - 节点边框颜色编码状态：`gray-300`=等待、`blue-500`=执行中（带脉冲动画）、`green-500`=完成、`red-500`=错误
  - 节点内部显示关键指标摘要（如提取的字段数量、质量评分等）

- **交互能力**：
  - 缩放/平移：支持鼠标滚轮缩放和拖拽平移
  - 小地图（MiniMap）：右下角显示全局小地图，方便在大型流程图中定位
  - 自动布局：使用 dagre 算法自动计算节点布局，保持从左到右的数据流向

### 6.2 ECharts（辅助图表）

**选择理由**：虽然 React Flow 处理流程图，但质量报告中的多维评分、数据分布统计等场景更适合用传统图表库展示。ECharts 功能全面、性能优秀，且对中文场景支持良好。

**使用场景**：

- **质量报告雷达图**：展示数据在完整性、一致性、规范性、准确性等维度的评分
- **数据提取统计柱状图**：展示各阶段提取的字段数量、成功率等统计信息
- **执行耗时瀑布图**：展示工作流各阶段的耗时分布，帮助定位性能瓶颈
- **数据流向桑基图**（可选）：展示数据从原始 PDF 到结构化输出的流转过程

## 七、页面架构设计

### 7.1 整体布局

采用经典的**三栏式布局**，参考 ChatGPT / VS Code 的布局思路：

```
┌──────────┬─────────────────────────────┬──────────────┐
│          │                             │              │
│  左侧栏   │        主工作区              │   右侧面板    │
│  (240px) │      (自适应宽度)             │   (400px)    │
│          │                             │              │
│ · 新建任务 │   ┌─────────────────────┐   │  · 节点详情   │
│ · 任务历史 │   │                     │   │  · 执行日志   │
│ · 设置    │   │   对话/工作流视图     │   │  · 数据预览   │
│          │   │                     │   │  · 质量报告   │
│          │   └─────────────────────┘   │              │
│          │                             │              │
│          │   ┌─────────────────────┐   │              │
│          │   │   输入栏             │   │              │
│          │   └─────────────────────┘   │              │
└──────────┴─────────────────────────────┴──────────────┘
```

- **左侧栏（Sidebar）**：可收起，宽度 240px。包含新建任务按钮、历史任务列表（按时间倒序）、底部设置入口。类似 ChatGPT 的对话列表
- **主工作区（Main Area）**：占据剩余宽度。上半部分为内容展示区（对话视图或工作流视图，可切换），下半部分为固定的输入栏
- **右侧面板（Detail Panel）**：可收起，宽度 400px。展示选中节点/Agent 的详细信息。使用可拖拽分隔条（Resizable Panel）调整宽度

### 7.2 核心页面

#### 页面一：对话式任务页（默认视图）

这是用户打开应用后看到的默认页面，类似 ChatGPT 的对话界面：

- **输入区**：底部固定的输入栏，包含多行文本输入框、文件上传按钮（支持 PDF 拖拽上传）、发送按钮
- **消息流**：用户消息和 AI 回复交替展示。用户消息靠右对齐（简短的任务描述），AI 回复靠左铺展（包含丰富的结构化内容）
- **AI 回复中的结构化内容**：
  - **阶段进度卡片**：当工作流执行到某个阶段时，展示一个可折叠的进度卡片，包含阶段名称、状态、耗时、关键输出摘要
  - **内嵌工作流缩略图**：在回复中内嵌一个迷你工作流图，点击可切换到全屏工作流视图
  - **数据预览表格**：提取结果以表格形式内嵌在回复中
  - **质量评分徽章**：用颜色编码的徽章展示各维度的质量评分

#### 页面二：工作流可视化页

通过视图切换按钮进入，展示完整的工作流拓扑图：

- **全屏 React Flow 画布**：占据整个主工作区
- **顶部工具栏**：包含缩放控制、自动布局按钮、视图切换（总览/子图详情）、执行回放控制
- **节点交互**：点击节点在右侧面板展示详情，双击节点展开/折叠子图
- **执行时间线**：底部可展开一个时间线条，展示各节点的执行时间段（甘特图风格），帮助理解并行/串行执行关系

#### 页面三：调试页

面向开发者的调试视图，提供工作流执行的全量信息：

- **步骤列表**：按时间顺序列出工作流执行的所有步骤（类似浏览器 DevTools 的 Network 面板）
- **状态快照对比**：选择任意两个时间点，对比工作流 State 的差异
- **LLM Prompt 查看器**：展示每次 LLM 调用的完整 Prompt（System + User + 上下文），以及模型的原始输出和解析后的结构化结果
- **错误追踪**：当某个步骤失败时，高亮显示错误链路（从触发错误的 Agent 到上游依赖的数据）

## 八、核心交互模式

### 8.1 任务执行过程的实时展示

这是整个前端最核心的交互场景。当用户提交一个数据提取任务后，前端需要实时展示工作流的执行过程：

**阶段一：任务提交**
- 用户输入自然语言描述 + 上传 PDF 文件，点击发送
- 输入栏上方立即出现一条用户消息
- 后端返回任务 ID，前端建立 WebSocket 连接
- 显示一个"正在分析您的需求..."的加载态

**阶段二：意图澄清（子图1）**
- 工作流进度条更新为"阶段 1/4：意图澄清"
- 展示一个可折叠的进度卡片，标题为"正在理解您的提取需求"
- 如果 Agent 需要向用户澄清需求（如"请问您需要提取哪类数据？"），则在对话流中插入一个交互式问题卡片，用户可以直接在对话中回答
- 意图澄清完成后，卡片收起显示摘要："已识别提取目标：XXX，涉及字段：YYY"

**阶段三：检索（子图2）**
- 进度条推进到"阶段 2/4：知识检索"
- 展示检索过程的可视化：检索到的文献列表、相关性评分、筛选过程
- 每个检索结果可以展开查看摘要和匹配片段高亮

**阶段四：数据提取（子图3）**
- 进度条推进到"阶段 3/4：数据提取"
- 展示 PDF 页面缩略图（如果有），标注提取区域
- 实时展示提取出的数据字段，以流式表格的形式逐步填充
- VLM 和 OCR 的提取结果并排展示，标注差异

**阶段五：数据质量评估（子图4）**
- 进度条推进到"阶段 4/4：质量评估"
- 展示质量评估的雷达图（实时更新各维度分数）
- 列出发现的数据质量问题（缺失值、异常值、格式不一致等）
- 如果触发数据清洗/标准化流程，展示清洗前后的对比

**阶段六：结果输出**
- 所有阶段完成，展示最终结果的汇总卡片
- 包含：提取数据表格、质量评分总览、导出按钮
- 用户可以在对话中追问或要求修改提取条件

### 8.2 流式文本渲染

- LLM 输出通过 WebSocket 逐 token 推送
- 前端使用 `requestAnimationFrame` 控制渲染频率，避免每个 token 都触发重绘
- 支持 Markdown 渲染：标题、列表、代码块（语法高亮）、表格、LaTeX 公式（使用 KaTeX）
- 流式渲染过程中显示一个闪烁的光标，完成后消失

### 8.3 可折叠的执行详情

采用**三级折叠**的信息架构，避免信息过载：

```
[完成] 阶段 1：意图澄清 (2.3s)                    ▼
  └─ [完成] 意图澄清 Agent (2.3s)                 ▼
       ├─ [完成] LLM 调用: 意图解析 (1.1s)         ▶
       ├─ [完成] Tool: 领域知识库检索 (0.8s)        ▶
       └─ [完成] LLM 调用: 结构化输出 (0.4s)        ▶
[进行中] 阶段 2：知识检索                             ▼
  └─ [进行中] 检索 Agent                             ▼
       ├─ [完成] Tool: 数据库检索 (1.2s)             ▶
       └─ [进行中] LLM 调用: 相关性评估...            ●
[等待] 阶段 3：数据提取                                ▶
[等待] 阶段 4：数据质量                                ▶
```

- 每一级都可以独立展开/折叠
- 展开时显示详情（如 LLM 的输入/输出、工具的参数/返回值）
- 折叠时只显示摘要（名称 + 状态 + 耗时）
- 正在执行的步骤显示旋转加载图标和实时文本流

## 九、后端技术栈

### 9.1 FastAPI

**选择理由**：FastAPI 基于 Python 类型提示自动生成 OpenAPI 文档，异步性能优秀，天然支持 WebSocket，与后端的 LangGraph 工作流同属 Python 生态，集成成本最低。

**关键接口设计**：

- **RESTful API**：
  - `POST /api/tasks` — 创建新任务（接收自然语言描述 + 文件上传）
  - `GET /api/tasks` — 获取任务列表（支持分页、筛选）
  - `GET /api/tasks/{task_id}` — 获取任务详情（包含各阶段结果）
  - `GET /api/tasks/{task_id}/quality` — 获取质量报告
  - `GET /api/tasks/{task_id}/export` — 导出提取结果
  - `POST /api/tasks/{task_id}/retry` — 重试失败的任务/步骤

- **WebSocket 端点**：
  - `WS /api/tasks/{task_id}/stream` — 实时推送任务执行事件流
  - `WS /api/tasks/{task_id}/logs` — 实时推送详细日志流

- **文件上传**：
  - `POST /api/upload` — 上传 PDF 文件，返回文件 ID 供任务创建时引用

## 十二、关键技术决策总结

| 决策点 | 选择 | 备选方案 | 决策理由 |
| --- | --- | --- | --- |
| 状态管理 | Zustand | Redux Toolkit, Jotai | 项目全局状态简单，Zustand 足够轻量，无 boilerplate |
| 服务端数据 | TanStack Query | SWR, Apollo | 功能最全面，支持 mutation、分页、无限滚动等 |
| 流程可视化 | React Flow | D3.js, Cytoscape.js | React 原生集成，API 友好，自定义节点方便 |
| 图表 | ECharts | Recharts, Chart.js | 雷达图等高级图表支持好，中文场景友好 |
| UI 组件 | shadcn/ui | Ant Design, MUI | 完全可控，无黑箱，方便深度定制 |
| 实时通信 | WebSocket | SSE, polling | 双向通信，适合实时日志和交互式澄清 |
| Markdown | react-markdown | marked, markdown-it | React 组件化渲染，插件生态好（数学公式等） |
